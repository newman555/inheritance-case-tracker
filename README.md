# 相続案件管理アプリ（Inheritance Case Tracker）

相続した不動産の案件を、紹介・相談会から引き渡しまで管理する、相続不動産のコンサルティング会社向けの社内アプリです（技術課題）。
「すべての選択肢を示し、売却を押し付けない」という考え方と相続の法定期限を、サーバー側のルールにしています。

## なぜこれを作ったか（Build vs Buy）
- 相談会の予約管理は既存のサービスで足りるので、**作らない**
- 案件の進め方と「提案の前に選択肢を比べる」仕組みはこの業務に固有で、既存のツールでは表しにくいので、**作る**

## 画面
| 画面 | URL | できること |
|---|---|---|
| パイプラインボード | `/` | ステージごとの案件一覧。「停滞」（14日以上動きなし）・「期限間近」（期限まで30日以内、または超過）の表示、依頼者・提携先での絞り込み |
| 新規案件 | `/cases/new` | 依頼者・物件・案件の登録 |
| 案件詳細 | `/cases/[id]` | ステージの移動、選択肢、相続人と同意、法定期限、履歴 |
| 比較シート | `/cases/[id]/compare` | 選択肢の横並び比較（売却は手数料を引いた額、賃貸は10年分）。印刷できる |
| 提携先 | `/partners` | 提携先ごとの案件数・完了件数、提携先の追加 |

## 業務ルール（サーバーで確認、`src/rules/`）
1. ステージは 受付 → 相談 → 提案 → 契約 → 完了 の順に1つずつ進む。飛ばす・戻す・完了後に動かすことはできない
2. 「提案」に進むには、種類の違う選択肢（売却・賃貸・建築・保有）が2つ以上必要
3. 「契約」に進むには、選択肢の決定、相続人1名以上、相続人全員の同意が必要
4. 選択肢を決定できるのは「提案」ステージだけで、同じ案件の選択肢に限る。決定した選択肢が変わると（最初の決定を含む）、相続人の同意はリセットされる
5. 紹介の案件は提携先が必須、相談会の案件は相談会の名称と日付が必須。死亡日と相談会の日付に未来の日付は使えない
6. 「提案」からは選択肢の変更と相続人の削除、「契約」からは相続人の追加と同意の変更ができない
7. 電話番号は書き方をそろえて保存する（全角・+81・ハイフンなど）。同じ番号で同じ名前なら同じ依頼者として扱い、名前が違えば拒否する
8. 仲介手数料は法定上限で計算：5%（200万円以下）、4%＋2万円（400万円以下）、3%＋6万円（400万円超）、さらに消費税10%
9. 法定期限（相続放棄3か月・準確定申告4か月・相続税10か月）は、法律の数え方どおり死亡日の翌日から数える。例：1/15 → 4/15、8/31 → 11/30、9/30 → 12/31
10. 入力チェック：必須項目、1円以上の金額、実在する日付、登録済みの種別・続柄

技術的な詳細：API の一覧（全13）は [API.md](API.md)、データの構造と処理の流れの図は [DIAGRAMS.md](DIAGRAMS.md) にあります。

## 技術スタック
**Next.js 15（TypeScript）・SQLite + Prisma 6・zod・Vitest 3・Tailwind CSS 4**
- 画面と API が1つのプロジェクトにあり、1つのコマンドで起動できる
- SQLite なので、アカウント・キー・Docker なしで動かせる。Prisma で PostgreSQL にも移行できる
- ルールは Next.js から切り離した関数なので、そのままテストできる
- 最新版（Next.js 16・Prisma 7）はセットアップ方法が大きく変わったため、動作を確認できるバージョンを使用

## 起動
Node.js 22 が必要です。
```bash
npm install
cp .env.example .env      # Windows: copy .env.example .env
npm run db:setup          # DB の作成、マスタデータの登録、Prisma Client の生成
npm run dev               # http://localhost:3000
```
- 最初に入っているのはマスタデータ（物件種別・提携先種別・続柄）だけです。まず `/partners` で提携先を追加してください
- DB の中身は `npx prisma studio`（http://localhost:5555）でブラウザから見られます
- `npm install` の最後に出る警告（9 vulnerabilities）は、テストやビルドに使う開発用ツールのもので、アプリを動かす部分ではありません。`npm audit fix --force` は実行しないでください（大きなバージョン更新が入り、動かなくなるおそれがあります）

## テスト
```bash
npm test      # Test Files 7 passed (7) / Tests 98 passed (98)
```
- ルールのテスト63件・API のテスト35件。すべてのルールについて「できる場合」と「断る場合」の両方を確認
- GitHub に push するたびに、GitHub Actions が自動で型チェックとテストを実行

## Supabase（PostgreSQL）への移行
Supabase にも、次の手順で移せます。
1. `prisma/schema.prisma` の provider を `postgresql` にする
2. `.env` の `DATABASE_URL` に Supabase の接続文字列を入れる（`.env` は Git に含めない）
3. マイグレーションは DB ごとに違うため、`prisma/migrations` を消して `npx prisma migrate dev --name init` で作り直す
4. 旧マイグレーション `lookups`・`relationships` のマスタデータの INSERT 文と、`japanese_labels` の UPDATE 文を、新しいマイグレーションに写す

## AI の利用
仕様（業務ルール・データ構造・API・テスト計画）を先に自分で決め、AI アシスタント（Claude Code）にはそれに沿った実装の補助とレビューを任せました。小さな単位で進め、AI の出力はすべて読んでから次へ進んでいます。確かめ方：
- すべてのルールに「できる場合」と「断る場合」のテスト、受付から完了までの API テスト、型チェック、ブラウザでの動作確認
- 法律やバージョンなどの事実は、公的機関のページや npm で確認
- AI のレビューの指摘は1件ずつ確かめ、正しいものだけ取り入れた

## 工夫・修正した点
- ルールを Next.js から切り離した関数にし、API とテストで同じルールを使う（画面もボタンの表示に同じルールを使う）
- 相続人が0人でも「全員が同意」が成り立ってしまう抜け道を、1名以上のチェックで防いだ
- ルールを満たした後に崩されないよう、ステージに応じて編集を止めた（相続人の削除は提案から）
- ステージの移動と履歴を1つのトランザクションで保存し、2人が同時に進めても二重に進まないようにした
- 仲介手数料は小数の誤差が出ないよう、整数で計算してから切り捨てた
- 法定期限を法律の数え方（翌日から数える）に直した（月末の死亡日で1〜3日早くなっていた）
- 操作の後、画面が新しいデータに変わるまでボタンを押せないようにした（二度押しでエラーや二重登録になっていた）

## 既知の簡略化
- 期限は死亡日から数える（法律上は「相続の開始を知った日」から）。期限が土日祝日に当たるときの延長は未対応で、表示が法定より遅くなることはない
- 仲介手数料は常に法定上限。800万円以下の特例（上限33万円）は未対応
- 同時編集の保護はステージの移動だけ（相続人・選択肢の変更と同時に起きる場合は未対応）
- 失注・キャンセル、ログイン、1案件に複数の物件は未対応
- 金額の上限は20億円（PostgreSQL の `Int` が32ビットのため）
- 画面は PC 向けのみ
